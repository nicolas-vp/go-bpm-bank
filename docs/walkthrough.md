# Запуск и прохождение примера

> Только учебные цели. Авторы не несут ответственности за решения на основе примера и последствия его использования. Не вводите реальные персональные данные.

## Запуск

Docker Compose:

```sh
cp .env.example .env
# Задайте пароль POSTGRES_PASSWORD в .env.
docker compose up -d --build
```

Две базы создаются при первом запуске нового тома: bank для движка и bank_core для мок-АБС. Стенд не зависит от баз обычного демо go-bpm. Остановка без удаления данных: `docker compose down`.

Локальные бинарники с существующим тестовым PostgreSQL:

```sh
make build
createdb bank
createdb bank_core

# В первом терминале. Подставьте реквизиты своего тестового PostgreSQL.
MOCK_DSN='postgres://bank:password@localhost:5432/bank_core?sslmode=disable' bin/mock-core-banking

# Во втором терминале.
BANK_DSN='postgres://bank:password@localhost:5432/bank?sslmode=disable' bin/gobpmbank
```

Приведённые DSN — образцы, пользователь bank должен существовать. BANK_ADDR / MOCK_ADDR меняют адреса (по умолчанию localhost:8090 / localhost:8091); MOCK_URL меняет адрес HTTP-зависимости банка. Таблицы создаются при старте. Чужие схемы не очищаются, но для примера нужны свои пустые базы.

## Обычный путь в консоли

1. Открыть http://localhost:8090/, прочитать учебную оговорку и перейти в консоль.
2. На вкладке «Запуск» выбрать обычный сценарий. Главный процесс — RetailAccountOpening; дочерние вручную не запускаются.
3. Перейти в «Задачи», задать пользователя `operator`, группы `operators`. Обновить список и взять IdentifyApplicant.
4. Нажать «Выполнить» и заполнить переменные ниже. Можно переключить стандартный редактор в режим JSON. Это обычный редактор переменных go-bpm, отдельной формы задачи нет.

```json
{
  "applicantName": "Учебный Клиент",
  "birthDate": "1990-01-15",
  "citizenship": "RU",
  "passportRef": "DEMO-DOCUMENT",
  "address": "Учебный адрес",
  "purpose": "Личные нужды",
  "taxResidency": "RU",
  "identityVerified": true,
  "documentsComplete": true
}
```

5. Автоматические проверки и DMN проходят без вмешательства; появляется ConfirmContract для operator.

```json
{"contractAccepted": true, "signedDocumentRef": "DEMO-SIGNATURE-REFERENCE"}
```

6. Открытие и постобработка выполняются автоматически. В «Экземплярах» отфильтровать RetailAccountOpening и открыть историю. Нажать на call activity, чтобы увидеть дочерний экземпляр и перейти в его историю. Итоговые переменные — в истории задач.

## Ручная проверка

Сценарий screening_match: после анкеты появляется ReviewClient. Переключиться на `aml`, группы `compliance`, взять задачу и заполнить:

```json
{"reviewDecision":"CONTINUE","reason":"Учебное совпадение разрешено как ложное","legalBasisCode":""}
```

Сценарий pep дополнительно создаёт AuthorizeClient. Пользователь `chief`, группы `supervisors`:

```json
{"reviewDecision":"CONTINUE","authorized":true,"reason":"Второй сотрудник проверил учебные сведения"}
```

Произвольные группы из claim не дают дополнительных прав. Но userId — выбираемая учебная личность, не защищённая учётная запись. Не публикуйте этот интерфейс как банковский рабочий контур.

## Уточнение, отказ и отказ клиента

- incomplete: на первой IdentifyApplicant передать documentsComplete=false. DMN запросит сведения, появится новая IdentifyApplicant. Во второй задаче отправить полную анкету с documentsComplete=true. Все проверки повторятся.
- tax_refusal: на приёме передать taxResidency="". Для ReviewClient: `{"reviewDecision":"DECLINE","legalBasisCode":"NK142_4_NO_TAX_DATA","reason":"Учебное непредставление запрошенных налоговых сведений"}`. Другие служебные основания произвольно подменять нельзя.
- withdrawn: в ConfirmContract передать contractAccepted=false. АБС не вызывается.

Сценарий выбирает поведение мок-сервисов, а не предопределяет решение сотрудника. Например, incomplete с сразу полной анкетой не заставляет её искусственно возвращаться. Клиентские данные и решение всё равно нужно заполнить.

## Сбои интеграций

lost_response: мок регистрирует счёт, первый HTTP-ответ — 503. Очередь повторяет шаг; обработчик запрашивает операцию по устойчивому ключу и продолжает с тем же счётом.

core_pending: статус PENDING, затем таймер PT1S, повторный опрос и OPENED. core_reject: результат REFERRED_CORE, не отказ по 115-ФЗ. tax_report_retry: первая попытка сообщения ФНС получает 503, повтор подтверждает тот же идемпотентный эффект.

В стандартной консоли доступны история и повтор упавшего шага: [документация сопровождения](https://go-bpm.tech/docs/running/). Не используйте отмену BPMN как замену закрытию зарегистрированного счёта.

## API

Запуск: POST /bank/api/applications с applicationId(UUID) и scenario. Остальные пользовательские операции — [стандартный API go-bpm](https://go-bpm.tech/docs/api/): GET /api/v1/tasks, POST /tasks/{id}/claim и /complete с userId и variables. Прямой POST запуска процесса через общий API запрещён: он обходил бы прикладную идемпотентность и позволял бы запускать подпроцессы без главного заявления.

Допустимые переменные и роли — [processes.md](processes.md). Неверный тип, чужое служебное поле и неподходящий кандидат отклоняются. Отдельных форм задачи, шаблонов документов или настоящей электронной подписи нет.
